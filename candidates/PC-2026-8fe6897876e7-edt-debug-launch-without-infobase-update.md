# Запуск отладки EDT без обновления конфигурации ИБ

- **Контекст:** программный запуск отладки 1С из EDT — через MCP, CLI или
  собственную автоматизацию — когда конфигурация базы намеренно должна остаться
  как есть.
- **Проблема:** EDT показывает модальный диалог обновления приложения, и кнопка
  по умолчанию в нём **обновляет конфигурацию информационной базы**. Автоматика,
  которая жмёт кнопку по умолчанию или просто ждёт исчезновения окна, тихо меняет
  состояние базы; на нелокальной базе это изменение видят все, кто с ней работает.
  Запуск при этом выглядит успешным, поэтому ошибку замечают не сразу.
- **Решение:** подтверждать только **точно опознанную** кнопку запуска без
  обновления, по её подписи в каждой поддерживаемой локали. Подпись не найдена —
  диалог отменяется, а не подтверждается кнопкой по умолчанию: отказ от запуска
  дешевле незаявленного изменения базы. Перехватчик ставится только на время
  вызова запуска и снимается в `finally`; при параллельных запусках приоритет
  отдаётся варианту, не изменяющему базу.
- **Проверка:** не «клиент запустился», а состояние базы до и после. Признак
  необходимости обновления, который EDT возвращает по проекту, обязан остаться
  прежним после запуска; в журнале EDT должна быть строка о нажатии именно кнопки
  запуска без обновления.

## Notes

Урок повторяется в любом проекте, где отладка 1С запускается не руками:
диалог принадлежит EDT, а не конкретной конфигурации, и кнопка по умолчанию в нём
одна и та же. Практика описывает контракт поведения, а не конкретную реализацию:
локальная доработка MCP EDT — лишь один способ его выполнить.

Границы: относится к запуску отладки при уже расходящейся конфигурации. Случай
«обновление действительно нужно» практикой не запрещён — он требует явного
намерения вызывающей стороны, а не согласия по умолчанию.

Evidence поднят до `E2` при review: подтверждений два и они разной природы —
автоматические unit-тесты на обе локали и на отказ от изменяющей кнопки, плюс
приёмочный прогон, выполненный дважды по одной схеме с проверкой состояния базы
после каждого цикла.
